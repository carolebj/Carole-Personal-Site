Les commentaires peuvent contenir des précisions plus récentes que le corps initial d’une tâche.

  • Rechercher une tâche existante avant d’en créer une afin d’éviter les doublons.
  • Ne mettre à jour que la tâche réellement travaillée et y joindre un commentaire bref : résultat, preuves, reste non vérifié et blocage éventuel.
  • Ne pas fermer une tâche à la simple existence d’un patch : les critères d’acceptation et les preuves doivent être satisfaits.
  • Ne pas créer, réaffecter ou reclasser massivement des tâches sans demande explicite.
  • Une priorité ou sévérité TickTick ne donne jamais, à elle seule, l’autorisation de toucher Production, main, Supabase ou Vercel.

Si TickTick et ce document semblent diverger, suspendre uniquement le point contradictoire, rapporter les deux formulations et poursuivre les parties indépendantes.

3. Lot 1A — routage, SEO de base et états introuvables

Libre d’action

Résultat attendu

Aucune URL inconnue ne doit afficher silencieusement un article, un service ou le premier contenu disponible. Le visiteur reçoit un état introuvable explicite, cohérent et non indexable.

C1 · C2 · H4–H6 · H16 · H18 · S04 · S05 · S07 · V04

Problèmes à corriger

  • Les slugs blog/service invalides peuvent se rabattre sur un contenu réel.
  • Le rewrite SPA sert index.html à toute route ; un composant 404 ne prouve donc pas un statut HTTP 404.
  • /dashboard n’est pas exclu de robots.txt et ne porte pas de noindex spécifique.
  • Un lien /#projects vise une cible absente ou incohérente.
  • Le dashboard bascule en démo locale si les variables Supabase manquent.

Changements autorisés

  • Supprimer tout fallback « premier item » sur les détails blog et service.
  • Router les slugs inconnus vers le composant NotFound et lui fournir titre, description, canonical et robots propres.
  • Ajouter Disallow: /dashboard et un noindex,nofollow dans le shell admin.
  • Corriger ou retirer /#projects selon la cible réelle déjà présente.
  • Actualiser public/llms.txt à partir des routes réellement publiques.
  • Rendre une build de production fail-closed si Supabase manque, tout en conservant un mode démo explicitement local/Preview si le contrat actuel l’exige.

Liberté technique

Cursor choisit le mécanisme React Router, les helpers de résolution, la forme des tests et la factorisation SEO. Il peut harmoniser NotFoundPage et ErrorPage avec les tokens existants si le comportement ne change pas au-delà du périmètre.

Limites et arbitrages

  • Ne pas migrer la SPA vers SSR/prerender dans ce lot.
  • Ne pas modifier les URLs linguistiques ou introduire /en/.
  • Ne pas prétendre avoir un vrai HTTP 404 si seul le rendu React est corrigé.
  • Le mode démo sans Supabase est un défaut de configuration/UX, pas une preuve de fuite de données réelles.

Critères d’acceptation

  • Un slug blog inconnu n’affiche aucun article réel.
  • Un slug service inconnu n’affiche aucun service réel.
  • La page introuvable possède title, description et robots adaptés dans le DOM.
  • La navigation retour/accueil reste fonctionnelle en FR et EN.
  • /dashboard est absent du sitemap et non crawlable.
  • La différence entre 404 visuel et statut HTTP est documentée honnêtement.

Preuves à joindre

  • Tests automatisés des résolveurs/slugs invalides.
  • Captures ou inspection DOM des métadonnées 404 et dashboard.
  • Résultat direct des routes en navigateur intégré, y compris après rechargement.
  • Si le statut HTTP est traité : preuve curl -I sur une Preview autorisée, pas seulement localhost.

4. Lot 1B — accessibilité structurelle, formulaires et langue

Libre d’action

Résultat attendu

Chaque route publique expose une structure sémantique unique et navigable ; les erreurs de formulaires sont identifiables, reliées aux champs et rédigées dans la langue active du site.

H7–H9 · AW-03 · AW-04 · AW-06 · AW-07 · CQ-02 · V01 · V09

Landmark principal

Conserver un seul <main> par document. Pour le shell public classique, la solution préférée est que Layout possède le landmark et que les pages rendent un conteneur neutre. L’Estimateur, le dashboard et les shells autonomes peuvent garder leur propre main lorsqu’ils ne sont pas imbriqués dans celui du Layout.

Skip-link

Ajouter avant la navigation un lien « Aller au contenu principal » visible au focus, ciblant un identifiant stable du landmark. Le focus après activation doit être perceptible et ne pas être masqué par le header fixe.

ContactForm

  • Donner un identifiant stable à chaque champ et à son message.
  • Appliquer aria-invalid seulement quand le champ est invalide.
  • Relier le message par aria-describedby.
  • Utiliser une zone role="alert" ou aria-live adaptée sans annoncer deux fois la même erreur.
  • Conserver le focus et le shake comme compléments, jamais comme seuls signaux.

Langue et erreurs

  • Ne pas afficher directement validationMessage du navigateur comme texte final : sa langue suit le système, pas nécessairement le site.
  • Mapper les erreurs requises/email/message vers les traductions du projet.
  • Préserver des messages Brief distincts en anglais au lieu d’un échec générique.
  • Rendre le fallback de chargement neutre ou bilingue sans dupliquer l’infrastructure i18n.

Contenu et titres

  • Rendre les liens génériques descriptifs dans leur contexte accessible.
  • Corriger les niveaux de titres quand la sémantique est incorrecte.
  • Ne pas réécrire la copy About : elle a été validée et publiée. Un changement de balise ne doit pas devenir une révision éditoriale.

Critères d’acceptation

  • Un seul landmark main sur chaque route publique testée.
  • Skip-link utilisable entièrement au clavier.
  • Tous les champs invalides ont nom accessible, état et description associés.
  • Erreurs cohérentes en FR puis EN, indépendamment de la langue macOS/navigateur.
  • Focus visible dans Navbar, Footer, formulaires, modales et contrôles custom touchés par le diff.
  • Aucune régression sous prefers-reduced-motion.

5. Lot 1C — réparations visuelles structurelles

Libre, avec invariants

Résultat attendu

Retirer les comportements qui entravent la navigation et réparer les états d’accessibilité sans aplatir la direction créative du site.

V03 · V06 · V09 · V11 · DS-01 partiel

Footer : supprimer le scroll hijack

Le footer intercepte aujourd’hui wheel/touchmove, appelle preventDefault() et pilote window.scrollTo(). Retirer cette prise de contrôle globale : l’utilisateur doit toujours pouvoir remonter ou descendre naturellement.

Footer : préserver l’intention

La vague colorée et l’idée d’un « pull beyond footer » temporaire sont validées. Cursor peut conserver une révélation visuelle déclenchée par intersection, progression de scroll passive ou interaction locale avec le shader, à condition qu’elle ne bloque, ne renvoie ni ne contraigne le scroll.

Focus et tokens

  • Utiliser le token sémantique --focus-ring au lieu d’un hex répété.
  • Conserver un contraste visible en clair et sombre.
  • Ne pas supprimer les outlines sans remplacement équivalent.
  • La migration de quelques états touchés est autorisée ; la refonte exhaustive du design system reste un lot séparé.

Contrastes sombres

Corriger les couples texte muted/surface et les cards Carnet uniquement avec des tokens ou variables cohérents. Vérifier les paires réelles ; ne pas éclaircir globalement tout le thème sombre sur une impression subjective.

Liberté technique

Cursor peut simplifier fortement la logique du footer, choisir IntersectionObserver, motion values ou CSS, et extraire des helpers. L’objectif est la liberté de scroll et la stabilité du rendu, pas la conservation ligne à ligne du mécanisme actuel.

Critères d’acceptation

  • Aucun listener global non passif n’annule wheel/touch pour le footer.
  • Le footer reste visuellement intentionnel en desktop, mobile et reduced-motion.
  • Le shader ne provoque pas de saut ou retour automatique.
  • Focus visible et contrastes vérifiés sur les composants touchés.

6. Arbitrages déjà rendus — à ne pas rouvrir silencieusement

Ne pas recompresser

Vidéo About : qualité d’image prioritaire

L’audit recommande de réduire le poids, mais des essais réels ont montré que les variantes 288 × 360 et 384 × 480 dégradent visiblement le rendu image-like sur écrans haute densité.

  • Actif accepté : src/assets/carole-about-motion.mp4, H.264/AVC avc1, 720 × 900, environ 6,2 MiB, 10 secondes.
  • Ne pas remplacer par HEVC/H.265 : Chrome/Linux doit pouvoir décoder la vidéo.
  • Ne pas réduire la résolution ou la netteté au nom d’un score de poids.
  • Optimisations autorisées : lazy-mount hors viewport, preload="metadata", poster statique, chargement conditionnel et mesure réseau.
  • Préserver le contrôle reduced-motion : pas d’autoplay/hover automatique, mais lecture explicite disponible.
Préserver l’intention

Footer : effet oui, contrainte de navigation non

La direction créative de la vague est validée. L’audit a raison sur l’interception du scroll, pas sur la nécessité de supprimer toute personnalité au footer.

CMS autoritaire

Contenus publics et bilinguisme

Lorsqu’une lecture Supabase réussit, le CMS est la source de vérité. Ne pas réintroduire un fallback i18n champ par champ qui masque des traductions absentes et fabrique un patchwork FR/EN. La politique de blocage à la publication reste à décider.

Aucune invention

Copy, clients, résultats et témoignages

Ne créer aucun KPI, client, témoignage, cas d’usage, autorisation ou attribution. La copy About est déjà validée ; les autres passes éditoriales disposent de tâches séparées et doivent être proposées avant publication CMS.

Turnstile d’abord

Anti-abus du formulaire de contact

Décision actuelle : Cloudflare Turnstile en mode Managed, vérifié côté serveur, en conservant le honeypot et les validations. Répondre par un succès neutre au honeypot pour ne pas instruire les bots. Ne pas ajouter Redis, Upstash ou un nouveau Worker avant qu’un abus réel justifie ce coût et cette complexité.

Coûts bornés

Traduction IA

Le flux serveur → Worker → AI Gateway → OpenAI et la confirmation de coût dans le dashboard sont à préserver. Ajouter un rôle éditeur explicite et des bornes cohérentes est souhaité ; ne jamais exposer une clé OpenAI au navigateur ni contourner les budgets/rate limits du fournisseur.

7. Sécurité — ce que Cursor peut préparer, sans appliquer

Règle de gouvernance. Le scan Codex Security profond a été interrompu pour maîtriser les crédits. Ses données partielles n’ont pas été validées et ne constituent pas un rapport. Le triage statique des 21 constats du troisième audit reste la base de planification, avec les niveaux ci-dessous.
ClasseConstatsTraitement autorisé
Confirmé dans le dépôtS01, S02, S03, S06, S10, S14Analyser le chemin, écrire tests et migration/config locale. Pour RLS : ne rien appliquer avant inspection live et export.
À vérifierS09, S11, S12, S15, S21Mesurer headers et limites effectives, documenter la portée du token, vérifier comptes/MFA en lecture seule. Ne pas présenter comme exploitation confirmée.
Autre catégorieS04, S05, S07, S08, S13, S16–S20Traiter comme SEO, dette ou defense in depth selon le cas. Ne pas gonfler la sévérité sécurité.

RLS et schéma

  • Inspecter d’abord les policies réellement appliquées, le signup et les comptes autorisés.
  • Exporter avant toute migration.
  • Préparer une migration additive pour remplacer « tout authenticated » par un rôle éditeur explicite.
  • Fermer l’INSERT anon legacy tout en préservant la lecture historique admin.
  • Les migrations, pas schema.sql, sont la source de vérité actuelle ; réaligner le fichier documentaire.

API, headers et stockage

  • Préparer une CSP progressive : report-only avant enforcement.
  • Ne pas ajouter une CSP stricte sans inventaire des scripts, styles, médias et services externes.
  • Vérifier la taille réelle du body contact au-delà du seul Content-Length.
  • Ajouter MIME/taille au bucket public media après lecture de la configuration live.
  • Préserver le webhook Resend signé, les limites d’attachments et l’échappement des emails sortants.

9. Recommandations de modèles Cursor — conseil, pas attribution rigide

Le modèle proposé indique le meilleur rapport aptitude/coût pour le type de travail. Cursor peut adapter ce routage si le contexte l’exige, mais le choix du modèle ne modifie jamais le périmètre, les garde-fous ou les preuves attendues.

Principe économique. Utiliser le mode standard/non-Fast pour les longues lectures, les lots autonomes et les revues complètes. Réserver Fast à une boucle courte où la latence bloque réellement le travail. Aux tarifs publics consultés le 27 juillet 2026, Composer 2.5 Fast coûte environ 6× son mode standard par token ; Grok 4.5 Fast coûte environ 2× en entrée et 3× en sortie. Fast n’améliore donc pas automatiquement la pertinence d’un long raisonnement.

Lot 1A · routage et 404

Par défaut : Composer 2.5 Standard implémente et teste. Si la frontière entre 404 React et vrai statut HTTP devient structurante, Grok 4.5 Medium réalise une courte analyse en lecture seule puis revoit le diff.

Lot 1B · accessibilité et langue

Par défaut : Composer 2.5 Standard traite landmarks, skip-link, formulaires et messages. Grok 4.5 Medium n’est utile qu’en revue transversale des choix de structure ou d’annonce accessible.

Lot 1C · footer et contrastes

Binôme recommandé : Grok 4.5 Medium propose le comportement minimal préservant l’intention ; Composer 2.5 Standard l’implémente et vérifie les variantes responsive/reduced-motion.

Lot 2 · sécurité et RLS

Après autorisation : Grok 4.5 High prépare le threat model et la matrice de policies en lecture seule ; Composer 2.5 Standard écrit tests et migration locale ; Grok High effectue la revue finale. Aucune application distante implicite.

Design system, dette et vidéo

Par défaut : Composer 2.5 Standard. Pour la vidéo, il peut optimiser le chargement sans réencoder. Grok Medium intervient seulement si le comportement de mouvement ou l’architecture des tokens est réellement remis en jeu.

Option sobre en crédits

Composer 2.5 Standard peut réaliser seul les Lots 1A et 1B avec les critères de ce document. Ajouter Grok uniquement pour les points ambigus ou la revue finale à risque, plutôt que de faire exécuter tout le lot deux fois.

Coordination

Un seul modèle écrit à la fois dans un même lot

Le second modèle intervient comme analyste ou reviewer après stabilisation du diff. Ne pas faire modifier simultanément les mêmes fichiers par Composer et Grok. La revue doit citer les critères du lot et signaler uniquement les écarts observables.

Grok 4.5 documente officiellement les efforts Low, Medium et High ; si le sélecteur Cursor ne les expose pas dans la session courante, choisir le mode de raisonnement disponible le plus proche. Pour Composer 2.5, les sources consultées décrivent une calibration d’effort adaptative : ne pas inventer un réglage Low/Medium/High absent de l’interface.

10. Protocole de vérification obligatoire

Un lot n’est pas terminé parce que le code paraît juste. Cursor doit fournir des preuves proportionnées au risque et distinguer ce qui a été exécuté de ce qui reste non observé.

Contrôles communs

npm run typecheck npm run test:unit npm run build npm run security:scan git diff --check

Ne pas lancer de formatter ou réécriture mécanique globale non prévue.

Contrôle CMS conditionnel

Si le diff touche src/admin, src/cms, le seed, les ressources CMS ou les pages Carnet :

npm run cms:verify

Exiger la sortie « Vérification dashboard OK », puis ouvrir l’unique AGENT_PREVIEW_URL dans le navigateur intégré de Cursor.

Matrice navigateur minimale

  • Desktop et mobile étroit ; clair et sombre.
  • Navigation clavier complète, focus visible et skip-link.
  • FR puis EN sur routes, erreurs et états de chargement.
  • prefers-reduced-motion activé.
  • Slugs invalides blog et services après navigation interne et rechargement direct.
  • Console sans nouvelle erreur ; aucun overflow horizontal introduit.
  • Pour le footer : wheel, trackpad, clavier, touch et retour vers le haut sans capture du scroll.
  • Pour la vidéo : poster, chargement différé, lecture disponible, H.264 720×900 préservé.
Revue indépendante avant livraison. Après les checks, relire le diff comme un reviewer distinct : périmètre, régressions, secrets, données, accessibilité, comportement responsive et écarts aux arbitrages. Ne pas committer automatiquement. Quand un jalon cohérent est prêt, signaler seulement qu’un commit pourrait être utile.
